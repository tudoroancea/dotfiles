# SDK projection fidelity and bounds

## Scope

This Phase 0B evidence uses Pi 0.82.1 `SessionManager.open()`, direct entries/tree/branch reads, and deterministic source-event fixtures. It makes no credential lookup or model request. The committed fixtures are intentionally small; large and hostile values are generated by tests. This layer is daemon observability/admission evidence, not a browser snapshot, operation, revision, cursor, or history data transfer object (DTO).

The representative session covers user and assistant messages, thinking, tool calls/results, custom and custom-message entries, an image, compaction, a two-child branch, model/thinking changes, and Agentflow/background output. The companion SDK source fixture covers retry, steer/follow-up queue, and settlement. Host-neutral provider snapshots are kept in a separately named fixture and are not represented as Pi SDK events. The fidelity test requires every durable JSON Lines value to round-trip unchanged through the public SDK manager and requires the bounded representative page to remain unchanged.

## Hard daemon-side thresholds

| Resource                                                                        | Hard limit |
| ------------------------------------------------------------------------------- | ---------: |
| Persisted session file                                                          |     64 MiB |
| Persisted JSONL line                                                            |      8 MiB |
| Entries per session                                                             |    100,000 |
| Entries considered per history page                                             |        100 |
| Serialized projected history page                                               |      1 MiB |
| Serialized single projected entry                                               |    256 KiB |
| Aggregate decoded image resource bytes per entry (provisional source admission) |      5 MiB |
| Images per entry (provisional source admission)                                 |          8 |
| Tool-result content per entry                                                   |    256 KiB |

The image values describe aggregate source-resource admission, not the browser JSON budget or decoded bitmap memory. The browser protocol will replace accepted image bytes with bounded opaque references or explicit omissions and deliver bytes through authenticated same-origin endpoints. Projected entry/page/frame limits therefore remain independent from image resource-byte, count, width/height, pixel, resolver-state, and response-concurrency limits. The current measurement helper still measures raw SDK entries before that projection exists, so an inline image can trip the 256 KiB projected-entry evidence limit first; daemon Phase 4 removes that temporary mismatch rather than raising JSON limits.

`src/observability/sdk-projection-bounds.ts` is the executable authority. Before `SessionManager.open()`, a resumed path is opened without following symlinks, required to be a regular file, and streamed in bounded chunks to enforce file, line, and entry limits. Its device, inode, size, modification time, and change time are checked again after SDK startup, and the SDK entry count is checked before readiness. Session byte/count violations do not trigger an unbounded read or response: history is explicitly degraded and only a bounded page can be considered. An entry violating entry, image, image-count, or tool-result limits is omitted whole and its reason is reported. Page construction stops before crossing its byte limit. The result carries `degraded`, all observed reason codes, and an omitted count; callers must not describe such history as complete. No value is silently truncated into misleading valid content.

## Measurements

Run:

```sh
apps/remote-session-daemon/scripts/measure-sdk-fixtures.mjs
```

The executable report includes source/projected bytes, entry/image/tool-result counts and bytes, tree/branch counts, generated 100,000-entry source size, bounded page size, degraded reasons, and process resident set size (RSS) before loading, after loading, and after page projection. RSS is evidence rather than a brittle pass/fail threshold because V8 allocation and host conditions vary. Tests enforce deterministic count/byte limits and positive RSS observations.

One local Node 26 run measured the 3.2 KiB fixture as 12 entries, one six-byte decoded image, 52 serialized tool-result bytes, one tree root, and a three-entry selected branch. A generated 100,000-entry source was about 25.4 MiB in JSON form; its bounded page was 100 entries/about 24.5 KiB. Observed RSS increased about 36.5 MiB while generating the source and about 0.3 MiB during page projection. These figures characterize the fixture, not a service-level objective; hard limits above remain stable and executable.

## Trusted local writer residual boundary

Root and working-directory device/inode identities and canonical paths are rechecked after asynchronous trust and immediately before registry creation. Resume files receive analogous no-follow identity and size checks around SDK opening. These checks close ordinary swap windows but do not make a malicious writer with permission to mutate an already opened file or approved project trustworthy; approved roots, session storage, and their local writers remain an operator-controlled trust boundary.

## Degraded-history contract

Degradation reasons are `session_bytes`, `session_entries`, `page_bytes`, `entry_bytes`, `image_bytes`, `image_count`, and `tool_result_bytes`. Oversized source remains Pi JSONL truth, but the daemon must expose only bounded, explicitly incomplete history. A future browser representation must come from the shared client package; this evidence deliberately defines no daemon-local browser wire schema or cursor.
